# EMA – revize skutečného stavu pošty, projektů, provozu a roadmapy
**19. 11. 2026 · zdroj: aktuální kód Ema main + otevřené GitHub Issues + uživatelská provozní pozorování**

## Pravidlo interpretace
- **Kód:** existuje přímo v repozitáři, je nezávisle dohledatelný.
- **Automatické testy:** ověřují vybrané scénáře a izolaci; nejsou důkazem provozu na Exonu.
- **Produkce:** jen výslovné ověření v reálné aplikaci (s doloženým nasazeným otiskem/SHA).
- **Chybí:** pokud implementace nemá požadované workflow ani prokazatelně funkční integraci.
- **Neověřeno:** funkce může být v kódu, ale nemáme přesnou produkční přejímku nebo reálný přístup k externí službě.

## Co již opravdu proběhlo
1. Nová Python Ema má na Exonu použitelný základ poštovního klienta, což dokládají uživatelské screenshoty.
2. Instalace PWA byla uživatelem potvrzena 17. 11. 2026; neznamená to ověření všech PWA scénářů.
3. PR #81 (Mail V1.2) a PR #84 (Mail V1.3) byly sloučeny do main a jejich vývojové scénáře prošly automatickými testy.
4. Aktuální Superadmin před Ops V1 zobrazoval firmy, účty, PWA diagnostiku a globální počty; **neměl spolehlivou evidenci živého release**.
5. /health vracel statickou verzi 0.1.0, a proto nebyl důkazem nasazení žádného z nových PR.

## Současné blokéry
**P0 / provoz:** doložit produkční SHA/fingerprint, schéma DB, konkrétní chyby a poslední běhy workeru. Ops V1 je cílená oprava, ale do doby nasazení nedokáže zpětně doložit starý stav. Následně přejímka Mail podle /docs/EMA_MAIL_V13_DEPLOY.md a test obnovy DB (#59).

**P1 / další vývoj:** Projektové workflow a akviziční kampaně; propojit s reálným obchodním cílem, nikoli přidávat další graficky hezké karty. Současné CRM a pipeline jsou základy, ne automatizovaný obchod.

**P2 / AI:** Fresh AI Engine napojit na schválený, auditem dohledatelný kontext. Každá změna či odeslání má být návrh → schválení → realizace → verifikace. Karel bude řešit issues, neřídit produkci bez přímého povolení.

## Navržené dokončení aktuální etapy
1. Nasadit Ops V1, pod superadminem otevřít a uložit chráněný manifest.
2. Porovnat skutečné souborové SHA256 s GitHub main, zapsat běžící commit i datum.
3. Dokončit poštovní přejímku s testovacími daty (bez produkčního hromadného Koše).
4. Do GitHub Issues zaznamenat u každé přijaté části **code complete / CI passed / production verified**; neuzavírat neověřené požadavky.
5. Zařadit další práci: **Projekty → akviziční kampaně → Fresh AI Engine**, společný stavební standard a schvalování implementací.
6. Rozšíření Fresh Feedback / Karel řešit až po skutečně dostupném API a rolích, aby nevznikal mrtvý formulář.

## Základní pravidlo verzí
Nikdy nesdělovat „nasazeno“ jen proto, že se PR sloučil do main. Manifest má ukazovat přesnou revizi nebo výslovně „neověřeno“. CI a provozní test zapisovat odděleně. O změnách práce mezi jednotlivými projekty nebude svědčit statický release popis, ale skutečná verze a audit provedených operací.
